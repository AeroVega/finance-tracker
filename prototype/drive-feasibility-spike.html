Google Drive storage experiment

Hard safety boundary

This experiment creates, reads, updates, and deletes only temporary synthetic test files. It never searches for, opens, or modifies the canonical Finance Tracker manifest or any ledger data. Use a dedicated test folder, not the folder containing personal financial records. No CSV uploads.

Tokens stay in page memory. Test file IDs are shown only so two browser sessions can coordinate a synthetic concurrency test. Do not paste credentials or real Drive IDs into public issues or source files.

2. Immutable object and retry safety

Create an invented text object with a pre-generated Drive ID. The experiment deliberately discards the first successful response, retries the same ID, expects HTTP 409, then reads back and verifies the exact SHA-256.

3. Durable transaction and recovery test

Creates a disposable synthetic manifest, stages an invented object, writes the append-only journal and immutable commit record, publishes the manifest last, then reopens the transaction from Drive and verifies the committed snapshot. This does not access the canonical database. It uses a temporary manifest and synthetic records only.

5. Raw REST If-Match probe

Use the shared synthetic race-test file ID above. This sends a deliberately stale If-Match value directly through fetch to the Drive REST API, then reads the file back. HTTP 412 means the precondition was enforced; a successful update means Drive accepted a deliberately stale validator. A browser/network error is inconclusive. The only possible mutation is the verified synthetic file's description.

Not tested.
