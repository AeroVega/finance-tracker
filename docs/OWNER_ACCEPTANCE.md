# Owner acceptance and release checklist

**Use invented data only.** This checklist does not authorize a merge, deployment, settings change, or real-data use. The operating plan is one designated Google account, one dedicated private database folder, one active device at a time, and manual backups. Use a *separate*, newly created empty synthetic folder for the restore rehearsal. Never select the real database for testing.

## 1. Before the owner session

- [ ] Record the full candidate SHA, exact served Pages build stamp and URL, and device/browser. Confirm the served build independently; green CI or Pages publication is not enough. If the expected build is not served, stop and record **Blocked**.
- [ ] Historical (synthetic-only profile, superseded by the 2026-11-24 GO record): the served build then showed “Synthetic workspace · Production financial storage disabled”, the Storage page shows no storage-class choice, and the served `js/release-profile.mjs` lists only `synthetic` and matches the candidate commit. A candidate that serves a private-database choice is out of scope for this checklist; record **Blocked**. See the [release gate](PERSISTENCE_DATA_CLASS.md#release-gate-what-static-code-can-and-cannot-enforce).
- [ ] Run exact-head CI and the required [guarded-code checks](GUARDED_CODE.md). Confirm that GitHub actually enforces the required fresh checks on `main`, rather than merely displaying green jobs. This single-owner project does not require independent approval; the owner reviews the exact-SHA diff before merge (see [guarded-code step 4](GUARDED_CODE.md#owner-and-reviewer-checklist)).
- [ ] Prepare one supported invented CSV, known expected rows/totals, a dedicated private synthetic folder, a fresh empty synthetic restore folder, and a safe invented wrong/unverifiable folder case. The reviewer can prepare evidence and fixtures without the owner’s credentials or private files. Use the [multi-year simulator rehearsal](SYNTHETIC_HISTORY_REHEARSAL.md) for a repeatable workload and encrypted-restore reference, not as device or provider acceptance.

## 2. One short live synthetic session

- [ ] Sign in using the designated test/owner account. Select the intended private synthetic folder. Verify a wrong or unverifiable folder is refused before any write, and cancel a selection without losing the previous verified context. Refusal by Google for an unapproved account is acceptable evidence for the provider gate; it is not evidence that the app saw and rejected that account.
- [ ] Select the invented CSV. Check mapping, coverage, and expected rows/totals; stage, then explicitly save. The reviewer verifies that original CSV bytes and locators never enter uploads, stored data, or portable backups, and that permitted normalized rows and provenance do persist.
- [ ] Release, confirm records are cleared from the workspace, then independently reopen the same folder. Verify the saved rows, totals, and provenance.
- [ ] Export an encrypted backup and confirm the download completes. After release, try a wrong password and confirm refusal without writes. Restore with the correct password to the fresh empty synthetic folder and independently reopen it. Compare records, totals, and provenance with the saved source; do not overwrite the source folder. Follow the [backup and recovery procedure](FULL_SNAPSHOT_BACKUP_RECOVERY.md) if an outcome is uncertain.

## 3. Close the remaining gates before GO

- [ ] **Owner-only:** In Google Cloud Console, confirm the actual account access mode, scopes, authorized origin, API restrictions, billing, quotas and usage; verify the dedicated Drive folder’s ownership, access and intended contents privately. On physical iPhone and iPad Safari, confirm scoped device behavior including release, browser restore, backup download and usable encryption cost. Do not publish account/folder identifiers, tokens, or private settings screenshots. See the [residual-risk checks](SECURITY_PRIVACY_OAUTH_COST_RECOVERY_REVIEW.md#residual-risks-before-any-activation) for the detailed device, OAuth and folder evidence.
- [ ] With invented data, leave a session unreleased. Explicit Open from the second device must refuse while the first marker is live or unverifiable. Stop the first device, wait for the heartbeat window to expire, and choose Open again. Verify recovery, marker read-back and the saved ledger, including pending publication resolution where applicable. Do not require manual Release after conclusive expiry. Release remains the faster orderly handoff.
- [ ] **Owner (AI review may assist):** Resolve the remaining [readiness gates](SECURITY_PRIVACY_OAUTH_COST_RECOVERY_REVIEW.md#residual-risks-before-any-activation), not just the happy path above. Include authorization expiry/revocation and reconnect, interrupted publication, privacy evidence, capacity and $0 operating cost, and the single-device/recovery limitations. Agree on manual backup cadence and recovery procedure; revise evidence if the candidate changes.
- [ ] **Release decision (separate from this candidate):** The private-database path is implemented but compiled out by the [release profile](PERSISTENCE_DATA_CLASS.md#release-gate-what-static-code-can-and-cannot-enforce). Live evidence for it requires a separately reviewed commit that changes only that profile, deployed from protected `main` and verified byte-for-byte as served. Its first live session repeats section 2 in **Private database** mode with invented data only, plus a synthetic-versus-private refusal in each direction and a designated-folder refusal. Static page code cannot verify approval; GitHub enforcement of the required checks and the owner's exact-SHA diff review must come first.
- [ ] **Owner decision:** Record **Pass**, **Fail**, or **Blocked** for each check with SHA, device/browser, sanitized result and any diagnostic ID. A fail, blocker, or missing evidence is not a pass. Keep real data **NO-GO** until the owner separately approves activation for the exact reviewed build, account, folder, storage format and backup/recovery procedure. A merge or synthetic pass is not activation.

[Current state](CURRENT_STATE.md) records earlier scoped acceptance, including the accepted 11-second open and 25-second save. Do not reopen unchanged work by default or apply its evidence to a different build, device, or workflow.
