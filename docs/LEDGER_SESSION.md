# Owned in-memory ledger sessions

**Implemented:** `createLedgerSessionOwner()` adds an optional cache for financial-event commands and read views. Existing pure canonical functions remain supported. It does not save, claim a storage session, rewrite history, or authorize production data.

## Ownership and boundaries

Create one owner for the application's current ledger. `owner.open(json, storageBinding)` first invalidates the prior session, then parses, deeply freezes and fully validates the supplied JSON. The nonempty binding string must identify the application's current verified lifecycle/copy/base, with a local generation. It is diagnostic binding, not remote authorization or a lock. A session cannot change its binding. Each open has a new owner generation; every method checks its handle is still current.

The integrating application must call `owner.invalidate()` **before** import, review/reversal, account changes, reload/recovery, lifecycle/copy changes, and every save attempt, before awaiting external work. Reopen only from a newly validated result and current binding. A failed or uncertain save must leave the session closed until a successful independently verified save or verified reopen; recovery requirements still apply. Keep the frozen draft separately for the existing warning/recovery UI. Storage ownership, exact-base verification and commit validation remain mandatory and unchanged. A caller that fails to route a boundary through the owner violates this contract; the module does not observe external storage automatically.

`session.snapshot()` returns a deeply frozen ledger, sharing unchanged records and collections with prior snapshots. Retaining an old snapshot is safe but retains memory and does not make it current. `validatedSnapshot()` and `exportJson()` perform full graph validation for boundary/save/export use. `effectiveActivity(id)` and `effectiveActivities()` return detached projected records; modifying them cannot alter the ledger or cached replay. `summarizePeriodsJson(scopesJson)` returns detached reports using the current replay. No Map, Set or mutable index is exposed.

`session.close()` and `owner.invalidate()` are idempotent and release the cache's graph/index references. Old handles reject further operations. Caller-retained snapshots still exist; this is not secure memory erasure. `session.binding()` returns a frozen generation, storage binding and revision record. `session.revision()` returns the current revision.

## Commands and failures

`session.applyBatchJson(batchJson, expectedRevision)` accepts a JSON array of `{command, eventId, recordedAt}` entries. The strings carry no caller getters or callbacks. IDs and clocks remain supplied by the application, just as with pure commands. An expected revision rejects an asynchronously prepared stale proposal. Accepted new events advance revision once per batch; empty or entirely idempotent batches do not advance it.

Commands run in order against private replay and refund indexes. Each uses the existing event builder, history validation, exact-amount/refund checks, idempotency signature and JSON checks. The original immutable graph remains published until every command succeeds. Only then does one replacement event array become visible. No external callback or await runs in the operation; reentrant preparation is rejected. Validation preserves the pure API's replay/refund-before-JSON error precedence.

Every preparation failure rebuilds all mutable indexes from the unchanged published graph. If reconstruction fails, the session closes and discards its references instead of allowing further commands against uncertain state. The original command error is returned. Allocation/process termination cannot be promised recoverable, but no partially prepared ledger is published. Parsing and revision errors occur before cache mutation. No persistence transaction occurs.

## Verification and limits

**Verified locally:** the session-specific tests cover immutable/deep alias boundaries, detached projections/reports, ordered/idempotent commands, failures at the beginning/middle/end of batches, stale revisions and generations, failed replacement, disposed handles, reconstruction failure poisoning, reentrant attempts, refund error precedence, 1,000 seeded pure/session differential commands, and dense one-year graph/projection/report equality.

The repeatable `node --expose-gc tests/benchmark-ledger-session.mjs session 10` and corresponding `pure 10` commands run separate CPU-only invented ten-year fixtures. Their final validated JSON hashes must match. Each reports opening, ten event commands, validated export, retained heap after GC, and whole-process high-water RSS. The latter includes fixture construction and is not the operation's true peak. These benchmarks do not prove a browser/mobile memory reduction or a network/storage speedup. Sessions deliberately retain replay/index state, trading persistent memory for lower repeated-command CPU. Opening, full export and pure fallback still scan the full graph.

**Verified:** the [final combined-branch regression](archive/PR30_PERFORMANCE_INTEGRATION.md) passed on both supported Node versions. **Open:** real Safari/mobile behavior, owner live acceptance and deployment. Local integration and independent review evidence follow below. This feature does not change the synthetic-only production gate.

### Local ten-year measurement (Node 24.22.1)

**Verified:** an invented ledger with 23,400 activities and 23,160 existing events produced identical final validated JSON SHA-256 (`e34574598458b5593d047166d184f8f6520d8ce28f7c8473569d4cf1ec32e2e7`) after ten identical commands in separate pure and session processes. Session command median was 0.34 ms; pure command median was 2,507 ms. Session opening took 2,822 ms including JSON serialization/parsing, freezing and validation; validated export took 1,066 ms versus 1,162 ms for pure. Other tests were running concurrently, so these are observed timings, not a controlled speedup claim.

Retained working-state heap after GC was 82.1 MiB for the session versus 70.7 MiB for pure: **persistent memory increased**, as expected for cached replay/indexes. After closing and dropping retained graphs, heap was 7.6/7.6 MiB respectively. Whole-process high-water RSS was 688/934 MiB, including fixture creation and export; this is not a true operation peak or proof of reduced browser memory. No storage/network timing was measured.

## Synthetic workbench integration

**Implemented:** the invented import workbench owns one session and uses it for event staging, effective activity views and reports. It retains the exact store, verified base and lifecycle references and checks online/ready ownership state before cache use. Imports, account changes, reviews/reversals, reload/recovery, release, lifecycle revalidation and every save attempt invalidate the cache before external work. A verified save opens a fresh generation; uncertainty keeps the frozen draft but no active session. Existing store validation, append-only checks, exact-base comparison, ownership gate and read-back remain unchanged.

The cache is optional. If opening it fails, ordinary pure functions still validate and operate on the retained ledger. A closed/poisoned handle is dropped rather than reused. No session or financial record is exported on `window`, saved in browser storage, or sent automatically. This integration does not paginate the full provenance tables or eliminate the full graph used by imports and persistence.

**Verified locally:** 107 nearby workbench/acceptance tests passed during integration. The final 33 handler tests include explicit cache preservation across local events/reads, invalidation before save awaits, uncertain-save draft retention, offline/base/release/reopen changes, optional-cache failure fallback, replacement imports, already-closed handles and failed preflight saves that retain the old base. An explicit fence prevents recovery with a declined reopen or a later pure edit from silently enabling the cache; only verified load/save clears it. Independent session review compared 2,000 batches (6,030 commands): 640 accepted batches and 1,360 matching rejections, including validation, views, reports, exports and failed-batch retry. Session engine's separate full Node 24 run passed 805 tests; final combined-branch regression is a separate gate.

**Verified in local Chromium 153.0.8010.0:** the real workbench, canonical engine and serializer with an invented storage stub completed load/import/event/report/save, an uncertain already-committed save followed by recovery without an extra write, offline invalidation, verified reopen and release. Two intended writes occurred, with no page errors. Five viewports (320×740, 390×844, 844×390, 768×1024 and 1440×1000) had no document overflow. Read-only test instrumentation observed cache state; the two external Google bootstrap requests were blocked, and no live Drive or OAuth action occurred. Real Safari/mobile memory, live synthetic Drive acceptance and deployment remain open.
